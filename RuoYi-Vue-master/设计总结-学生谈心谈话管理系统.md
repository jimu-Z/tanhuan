## 1. 项目概述

**学生谈心谈话管理系统** 是部署在 RuoYi-Vue 低代码平台上的一套辅导员工作数字化工具。核心业务围绕 **学生信息管理 → 发起谈话 → 记录反馈 → 跟进管理 → 数据可视化（仪表盘/大屏/预警）** 形成完整闭环。

### 1.1 技术栈

| 层级 | 技术 |
|------|------|
| 后端框架 | Spring Boot 3.x + MyBatis |
| 权限认证 | Spring Security + JWT (HS512) |
| 数据库 | MySQL + Druid 连接池 |
| 缓存 | Redis（Token 缓存、用户信息缓存） |
| 前端框架 | Vue 2.x + Element UI |
| 图表 | ECharts |
| 文档导出 | Apache POI (XWPF) + 模板占位符替换 |
| Excel 导入 | Apache POI (SS) + WorkbookFactory |

### 1.2 代码规模

- **后端 Java 文件**：约 33 个（controller 5 + domain 6 + service 9 + mapper 5 + XML 5 + DocxService 1 + constant 1）
- **前端 Vue 文件**：约 19 个（api 6 + views 13）
- **总代码行数**：约 8,500 行

### 5.2 [CRITICAL] `findOrCreateDept` 中 `ancestors` 计算错误

**文件**：[TalkStudentServiceImpl.java](file:///f:/kaifa/XueXiaoTanHuan/RuoYi-Vue-master/ruoyi-system/src/main/java/com/ruoyi/talk/service/impl/TalkStudentServiceImpl.java#L606-L612)

**问题**：当 `findOrCreateDept("计算机学院", 100L, "college")` 被调用且 100 号部门已在数据库中存在时，代码会走到 `parentDept != null` 分支，生成 `ancestors = "0,100,100"`（重复拼接了 100），导致部门树路径错误。

**根因**：条件判断顺序错误 — 应该先判断 `TOP_DEPT_ID`，再查询父部门。

**修复**：调整判断顺序，`TOP_DEPT_ID` 优先判断，避免重复拼接。

```java
// 修复前
SysDept parentDept = sysDeptMapper.selectDeptById(parentId);
String ancestors = "0";
if (parentDept != null) {
    ancestors = parentDept.getAncestors() + "," + parentId;  // 可能产生 "0,100,100"
} else if (parentId.equals(TOP_DEPT_ID)) {
    ancestors = "0,100";  // 此分支永远不会被顶层部门已存在的情况触发
}

// 修复后
String ancestors;
if (parentId.equals(TOP_DEPT_ID)) {
    ancestors = "0,100";
} else {
    SysDept parentDept = sysDeptMapper.selectDeptById(parentId);
    ancestors = parentDept != null ? parentDept.getAncestors() + "," + parentId : "0," + parentId;
}
```

## 6. 已识别的架构隐患与改进建议

### 6.1 [WARNING] 手动数据权限实现存在 SQL 注入风险

**文件**：
- [TalkSessionServiceImpl.java](file:///f:/kaifa/XueXiaoTanHuan/RuoYi-Vue-master/ruoyi-system/src/main/java/com/ruoyi/talk/service/impl/TalkSessionServiceImpl.java#L51-L72)
- [TalkStudentRecordServiceImpl.java](file:///f:/kaifa/XueXiaoTanHuan/RuoYi-Vue-master/ruoyi-system/src/main/java/com/ruoyi/talk/service/impl/TalkStudentRecordServiceImpl.java#L37-L58)

**问题**：两个 Service 的 `applyDataScopeFilter()` 方法通过字符串拼接直接将值写入 SQL 片段：

```java
talkSession.getParams().put("dataScope",
    " and ts.create_by = '" + username + "'");
// ...
" where (d.dept_id = " + deptId + " or find_in_set(" + deptId + ", d.ancestors))"
```

这些字符串最终通过 MyBatis 的 `${params.dataScope}`（非参数化语法）注入到 SQL 中。

**当前风险评级**：**中等**。`username` 来自 `SecurityUtils.getUsername()`（Spring Security 上下文），`deptId` 来自 `SecurityUtils.getDeptId()`（Long 类型），两者均非直接用户输入。且 username 做了 `replace("'", "''")` 转义。

**但仍存在潜在风险**：
1. 如果数据库中存储了恶意构造的 username，可能被用于注入
2. 违反了 OWASP 防御深度原则 — 应始终使用参数化查询

**建议改进**：统一使用 RuoYi 框架的 `@DataScope` 注解 + `DataScopeAspect` 切面方式，而非手动拼接 SQL。已在 `TalkStudentServiceImpl.selectTalkStudentList()` 中正确使用了 `@DataScope(deptAlias = "d")`，其他两个 Service 应跟进。

### 6.5 [INFO] `TalkStudentServiceImpl.importExecute()` 事务设计需优化

**文件**：[TalkStudentServiceImpl.java](file:///f:/kaifa/XueXiaoTanHuan/RuoYi-Vue-master/ruoyi-system/src/main/java/com/ruoyi/talk/service/impl/TalkStudentServiceImpl.java#L256-L365)

**问题**：
1. `@Transactional(rollbackFor = Exception.class)` 标记了整个方法，但方法内部用 `try-catch` 吞掉了所有异常，事务永远不会回滚。
2. 部门创建（`findOrCreateDept`）发生在学生校验之后但学生插入之前，如果学生因重复被跳过，已创建的部门成为孤儿记录。

**影响**：
- 事务注解实际不生效（异常被吞）
- 批量导入中断时可能留下无用的部门

**建议**：
- 移除方法级别的 `@Transactional`，或改为仅在每行成功时使用 REQUIRES_NEW 的事务
- 部门创建逻辑应改为惰性创建（仅当学生插入成功时才创建）
- 导入失败行应包含明确的行号标识

### 6.7 [INFO] 导入预览与执行的数据传递方式不安全

**文件**：
- [TalkStudentController.java](file:///f:/kaifa/XueXiaoTanHuan/RuoYi-Vue-master/ruoyi-system/src/main/java/com/ruoyi/talk/controller/TalkStudentController.java#L146-L159)
- [TalkStudentServiceImpl.java](file:///f:/kaifa/XueXiaoTanHuan/RuoYi-Vue-master/ruoyi-system/src/main/java/com/ruoyi/talk/service/impl/TalkStudentServiceImpl.java#L254-L373)

**问题**：导入流程采用"预览→确认→执行"两步式设计：
1. 预览阶段解析 Excel 并返回 `previewRows` + `fieldMapping`
2. 执行阶段前端将 `confirmedRows` 回传给后端插入

**隐患**：前端可以修改 `confirmedRows` 中的数据再提交，绕过后端校验。虽然代码中有部分后端校验（学号重复、手机号格式），但缺少与预览数据的完整性校验（如确认传入的数据是否与预览中的一致）。

**建议**：预览时生成一个 import token，执行时携带 token 从缓存获取原始解析数据，而非依赖前端传回的数据。
